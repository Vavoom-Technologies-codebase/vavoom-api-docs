Overview

Vavoom API

The Vavoom API lets you read and manage drive-thru operations data — brands, locations, hardware, orders, and customers. It's built on ASP.NET Core (.NET 6) and speaks JSON over REST.

Base URLhttps://api.vavoom.io
FormatJSON over REST
AuthOAuth 2.0 / OpenID Connect (bearer tokens)
VersioningNone — one unversioned API surface.
Rate limitsNone currently enforced. See Integration best practices.
This document covers the resources available for integration. A full interactive reference is available once your integration is onboarded — talk to your Vavoom contact for access.
Getting started

Authentication

Vavoom authenticates every request with an OAuth 2.0 bearer token — there is no separate API-key model. As part of onboarding, Vavoom issues your integration its own OAuth client using the authorization_code grant with PKCE. You get a token by completing that flow, then send it as an Authorization header on every call.

Token endpoint

POST /connect/token

Exchange an authorization code for an access token using the client credentials Vavoom provisions for your integration.

Field
grant_typestring — authorization_code
client_idstring — issued to your integration
client_secretstring — issued to your integration
codestring — from the authorize redirect
code_verifierstring — PKCE verifier
EndpointURL
Authorizehttps://api.vavoom.io/connect/authorize
Tokenhttps://api.vavoom.io/connect/token
ScopeVavoom
Request  ·  curl
curl https://api.vavoom.io/connect/token \
  -d grant_type=authorization_code \
  -d client_id="{YOUR_CLIENT_ID}" \
  -d client_secret="{YOUR_CLIENT_SECRET}" \
  -d code="{AUTH_CODE}" \
  -d code_verifier="{PKCE_VERIFIER}" \
  -d redirect_uri="{YOUR_REDIRECT_URI}"
Response 200 OK
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 36000
}
Using the token
curl https://api.vavoom.io/api/app/brand \
  -H "Authorization: Bearer {ACCESS_TOKEN}"

Errors

Vavoom uses conventional HTTP status codes: 2xx for success, 4xx for a problem with the request, 5xx for a problem on Vavoom's end.

The error object

Attribute
error.codestring, nullable
error.messagestring, nullable
error.detailsstring, nullable
error.dataobject, nullable
error.validationErrorsarray, nullable — present on validation failures
  ↳ messagestring, nullable
  ↳ membersstring[] — the field name(s) that failed
StatusMeaning
400Bad request — usually a validation error. Check validationErrors.
401Missing or invalid bearer token.
403Token is valid but the caller isn't authorized for this location/resource.
404No resource with that id.
500Server-side error. Safe to retry with backoff.
Response 400 Bad Request
{
  "error": {
    "code": null,
    "message": "Your request is not valid!",
    "details": null,
    "data": {},
    "validationErrors": [
      {
        "message": "'Name' should not be empty.",
        "members": ["name"]
      }
    ]
  }
}

Pagination & sorting

Every list endpoint (GET /api/app/{resource}) accepts the same three optional query parameters and returns the same wrapper shape.

List query parameters

ParameterType
SkipCountoptionalinteger — offset into the result set
MaxResultCountoptionalinteger — page size
Sortingoptionalstring — e.g. name desc

Response wrapper

itemsarray, nullable
totalCountinteger (int64)
Request  ·  curl
curl -G https://api.vavoom.io/api/app/brand \
  -H "Authorization: Bearer {ACCESS_TOKEN}" \
  -d SkipCount=0 \
  -d MaxResultCount=20 \
  -d Sorting="name asc"
Response 200 OK
{
  "items": [ { "...BrandDto" }, { "..." } ],
  "totalCount": 47
}

Idempotency

Idempotency keys are not currently supported — there is no Idempotency-Key header and no server-side request deduplication. A retried POST or PUT is processed as a new request.

If your integration retries on timeout or a 5xx response, design your writes to be safe to repeat — for example, check for an existing record before creating one. We recommend planning for this in your integration rather than assuming retries are deduplicated.

Integration best practices

A few things to design for up front.

  • Build in your own retry backoff. There's no rate limiting on the API today, but a well-behaved client should still back off on repeated failures rather than retry immediately in a loop.
  • Design writes to be safely repeatable. There's no idempotency-key support yet — see Idempotency.
  • Use authorization_code with PKCE for your OAuth flow, and keep your client secret server-side only.
  • Treat enum fields as opaque integers until you've confirmed the value mapping with your Vavoom integration contact.
